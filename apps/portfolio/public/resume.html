1 디자인과 개발 사이에서, 프론트엔드를 선택한 이유

저는 산업디자인을 전공한 뒤 뉴미디어디자인과 응용소프트웨어를 복수전공하며 자연스럽게 디자인과 개발 사이의 접점을 탐구해 왔습니다. Figma로 시안을 그리고 직접 코드로 구현하는 과정에서, 내가 만든 것이 화면에 살아 움직이는 순간의 즐거움을 알게 되었습니다. 그 즐거움이 지금도 저를 프론트엔드 개발로 이끄는 가장 강한 동기입니다.

단순히 주어진 디자인을 마크업하는 것을 넘어, 사용자 경험을 코드로 설계하는 개발자가 되고 싶다는 목표로 TypeScript, React, Next.js를 깊이 있게 학습해 왔습니다. 포트폴리오 사이트를 Turborepo 기반 모노레포로 직접 설계한 것도, 실무에서 통하는 아키텍처 감각을 직접 체득하고 싶어서였습니다.

2 팀 프로젝트에서 배운 것 — 코드 품질과 협업

SOSTeam 동아리에서 딤홈 쇼핑몰 프로젝트를 진행하며 처음으로 11인 규모의 협업을 경험했습니다. React + TypeScript + GraphQL 스택을 사용했고, 저는 프론트엔드와 프로젝트 테마를 담당했습니다.

가장 기억에 남는 것은 TypeScript 인터페이스를 선제적으로 설계했을 때입니다. 팀원들이 작성한 Product 관련 인터페이스들을 보다 보니 공통 속성이 반복되는 구조가 눈에 띄었습니다. 이대로 두면 나중에 한 속성을 바꿀 때 여러 타입을 모두 찾아 수정해야 하는 비용이 생긴다고 판단했고, 공통 속성을 담은 ProductLayerInterface를 먼저 설계한 뒤 ProductCategoryProps, ProductContentProps, ProductInfoProps가 이를 extends하도록 구조를 잡았습니다. 이 경험을 통해 "지금 동작한다"와 "나중에도 안전하다"는 다르다는 것을 배웠습니다.

3 스스로 설계하고 배포까지 — 모노레포 개인 프로젝트

팀 프로젝트 외에 개인적으로 Next.js 15 + Tailwind CSS v4 기반 포트폴리오 사이트와 칸반 일정 관리 앱 Taski를 Turborepo 모노레포로 구축하여 Vercel에 배포했습니다. 단순한 포트폴리오를 넘어, 실무 아키텍처를 직접 구현해보는 실험이었습니다.

이 과정에서 예상치 못한 문제를 만났습니다. apps/portfolio에서 packages/ui의 Tailwind 클래스가 빌드 시 purge되어 스타일이 사라지는 것이었습니다. 원인은 Tailwind가 기본적으로 현재 앱의 소스만 스캔하기 때문이었고, globals.css에 @source 지시자로 UI 패키지 경로를 명시하여 해결했습니다. 에러 메시지 하나 없이 스타일만 증발하는 문제라 원인 파악에 시간이 걸렸지만, 덕분에 Tailwind v4의 빌드 파이프라인을 깊이 이해하게 되었습니다.

Taski에서는 딤홈 쇼핑몰에서 배운 드래그앤드롭 패턴을 다시 적용하되, 이번에는 상태 관리 라이브러리를 Recoil 대신 Zustand로 선택했습니다. 보일러플레이트가 적고 구조가 단순한 Zustand가 개인 프로젝트 규모에 더 적합하다고 판단했고, 두 라이브러리의 트레이드오프를 직접 비교하며 상황에 맞는 기술 선택의 감각을 키웠습니다.

4 배움을 멈추지 않는 개발자

저는 아직 신입이고, 모르는 것이 많다는 것을 압니다. 그래서 더욱 솔직하게, 그리고 적극적으로 배우려 합니다. 팀 프로젝트에서 코드 리뷰 의견을 받으면 왜 그런지 이해하고 나서 수정하는 습관을 들여왔습니다. 단축 네이밍이 가독성을 해친다는 피드백을 받은 이후 PR 커밋 메시지부터 변수명까지 명시적으로 쓰는 것을 원칙으로 삼게 된 것도 그 과정에서 생긴 변화입니다.

디자인을 알고, 사용자 시각에서 UI를 바라보며, 구체적인 트러블슈팅 경험이 있는 신입 프론트엔드 개발자로서 — 빠르게 팀에 기여하고, 함께 성장하고 싶습니다. 기회를 주신다면 최선을 다하겠습니다.
